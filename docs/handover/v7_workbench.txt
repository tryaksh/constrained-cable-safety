=======================================================================
Turn a measured result into something an engineer can USE and a stranger can
UNDERSTAND in two minutes, then close the project.

Three deliverables, in this priority order:

  A. THE DEMONSTRATION. A video and a still figure where every number traces to

  2. Every claim the repository makes is still one the measurements support.
If those conflict, the second wins. A demo that overstates is worse than no demo.

3. WHAT YOU ARE SHOWING - THE NUMBERS THAT CARRY THE STORY
=======================================================================
Read README.md, then evidence/cable_perception_v4.json and
evidence/cable_sequence_v5.json, then whatever V6 produced. The story has three
beats and they are all measured:

  BEAT 1 - ONE NUMBER IS ENOUGH. 16,080 pre-registered requests. A single scalar
  with a margin sized from the estimator's declared error is not beaten by any
  richer representation, at any error level, on any of three constraint shapes.
  The ~30,000-parameter network over the whole cable centreline is significantly
  WORSE on clip retention: bootstrap gap 0.074, interval excluding zero.

  BEAT 2 - IT MATTERS MOST WHEN YOU CHAIN MOVES. 720 sequences. Every one of the
  240 unfiltered sequences pulled the cable out of the clip - a rate of 1.000 at
  every error level - against 0.400 to 0.569 filtered. This is the side-by-side
  the video is built around, and it is honest because it is universal.

  BEAT 3 - AND THE CHECK IS NOT THE WHOLE STORY. The clip budget stops composing
  at 2 mm error (per-step rate rising 0.089, past the 0.05 margin) while
  curvature and load hold. And post-hoc, how greedily the supervisor spends what
  the filter allows moved the outcome further than representation did: 8 clips
  lost instead of 32, 72 routes completed instead of 48. Label that exploratory
  ON SCREEN as well as in the record.

DO NOT let the demo imply beat 3 is a certified result. It is not. A caption that
says "not pre-registered" costs nothing and is the difference between a portfolio
piece an engineer trusts and one they discount.

5. STAGE B - THE WORKBENCH        done-condition: artifacts/showcase/tool.json
=======================================================================
A local engineering tool, `scripts/workbench.py`, that an engineer clones and
runs. Not a web app - a Python program using MuJoCo's own viewer.

  WHAT IT DOES: load the cell from config; let the user move a clip, change cable
  slack, and pick an error level; show the safety layer's envelope over the action
  space; run the route; report per-constraint budget spent and the outcome.

  HOW IT RENDERS: `mujoco.viewer.launch_passive` is present in this environment
  (MuJoCo 3.3.7). Controls can be a simple parameter panel or keyboard bindings -
  do not build a GUI framework dependency.

  A CONSTRAINT YOU CANNOT ESCAPE: you have no display. You CANNOT run the viewer
  and see it. So architect the tool so everything except the window is testable
  headlessly: a `WorkbenchSession` class that loads, mutates, runs and reports,
  with the viewer as a thin shell over it. Unit-test the class. Then the one
  untested line is `launch_passive`, and the owner can run it.
  SAY CLEARLY IN THE FINAL SUMMARY that the interactive window was never executed
  in-session. Do not claim you verified something you could not see.

  IT MUST BE PARAMETRIC. V6 was told to keep clip positions in config rather than
  code. If that did not happen, fix it here before building on top.

VERIFY: headless tests covering load, mutate a clip position, re-run, and report.
Plus one end-to-end headless run producing the same numbers as an evidence record
for an unmutated cell.

7. STAGE D - USD EXPORT FOR OMNIVERSE, IF TIME REMAINS
=======================================================================
The owner wants the option of rendering this in Isaac Sim / Omniverse LATER, for
visual quality, WITHOUT moving the physics. That path is verified and cheap.

  MuJoCo 3.3.7 ships `mujoco.usd.exporter`. It needs two packages beside it that
  are NOT currently installed in the cable venv: `usd-core` (provides `pxr`) and
  `pillow`. Both resolve cleanly - usd-core 26.8 was checked.

  INSTALL THEM IN A SEPARATE VENV, NOT IN .deps/cable-venv. That venv's exact
  package set is recorded in every run manifest's native_environment block and
  the project's provenance depends on it not drifting. A render-only venv with
  mujoco==3.3.7 + usd-core + pillow + numpy is the right shape; it was built and
  exercised during the v6 preparation.

  THE GOTCHA, which will waste twenty minutes otherwise: pass `output_directory`
  as a RELATIVE name and `output_directory_root` as its absolute parent. Give it
  an absolute `output_directory` and it joins them into `./C:\...` and throws a
  path error from inside OpenUSD.

  VERIFIED WORKING: 200 stepped frames of a scene carrying CAD visual meshes over
  primitive collision geometry exported to a single ~300 KB .usd stage.

  SCOPE IT HONESTLY: this is a rendering export. It does not make the project an
  Isaac Sim project, and nothing measured in MuJoCo may be described as validated
  in Omniverse.
